# OCaml-owned UI defaults

## Problem

The shared UI defaults implementation defines its main constants in JSON and
resolves omitted widget values in Swift. Surface opacity and some color alpha
values remain in Swift. The user requests that all shared defaults be defined
in bonsai-ui OCaml code. After discussing constructor-time resolution, the user
confirmed that themeable defaults must instead be inherited through Theme;
widget constructors must retain omitted values as unspecified.

A concrete OCaml argument default loses the distinction between omitted and
explicit values before a parent `View.theme` is applied. The existing contract
allows nearest-scope numeric overrides to affect omitted values. The user selected
scoped Theme inheritance, superseding the constructor-default proposal.

## Proposal

Retain scoped Theme inheritance and make the OCaml Theme module the single source
for the six shared style families. The selected implementation follows below.

## Decision

- OCaml is the authoritative source for the shared icon, interactive bounds,
  text-role, color-role, spacing and Surface defaults discussed in the
  [shared-default decision](../../implemented/feature/2026-09-15-shared-ui-defaults.md).
- The JSON source and JSON-to-OCaml path are removed. Native baseline data is
  generated by evaluating the OCaml Values module. No independent handwritten
  native default table is retained.
- Omitted themeable widget properties survive the wire. Resolve explicit
  widget properties before the nearest Theme overrides and OCaml-owned defaults.
- Theme now covers previously hardcoded Surface opacity, material/shadow
  alpha, symbol rendering, default text role, and per-role foreground/italic.
  Recipe material/shape/background/tint-alpha choices also belong to Theme.
  Plain and rich text now share scoped typography.
- Use `Theme.Defaults.Values` as the central OCaml declaration: adding a
  standalone `default.ml` would require editing the explicit module list in
  `ocaml/ui/dune`, which the repository instructions prohibit without an explicit
  request to modify Dune files. The user gave `default.ml` as an example location.
- Keep native execution of Dynamic Type, Bold Text, semantic system colors,
  iOS-only minimum bounds, compact controls and material rendering. Project
  values and recipe choices belong to OCaml; platform behavior belongs to the
  renderer.
- Behavior tests cover constructor omission, explicit overrides, invalid inputs,
  nested scopes and reactive theme-only updates. [Acceptance evidence](../../../theme-owned-defaults-acceptance.md)
  records the completed checks and the physical-device availability limitation.

## Alternatives considered

### Concrete constructor defaults

Matches the requested optional argument form directly. Shared numeric values are
fixed when widgets are constructed. Theme numeric overrides must be removed or
replaced with an explicitly supplied constructor configuration.

### Retain deferred scoped defaults

Preserves the current nested Theme behavior, but needs a typed default reference
or equivalent deferred representation instead of a plain float argument default.
The OCaml declaration can still own the values, but this changes the requested
constructor form or retains additional resolution machinery.

## Acceptance criteria

- OCaml contains the authoritative declarations for all previously discussed
  shared default values and recipe choices.
- Every affected constructor preserves omission and explicit overrides without
  relying on independent Swift constants. Native generated defaults are derived
  by evaluating the OCaml declaration, with no JSON source or duplicate table.
- JSON and obsolete generation/resolution paths are removed.
- Note, Mail and Gallery retain their intended application overrides.
- Native appearance/accessibility behavior remains verified.
- Tests cover the chosen construction and theme semantics through real widget
  creation and protocol/rendering boundaries.
- No protected spec or Dune file is modified under current authorization.

## Consequences

Protocol 8 replaces the prior sparse Theme and inherited text/symbol encodings.
Consumers must use matching builds. Surface's version 3 payload remains unchanged.
Raw surfaces now use the Unstyled Theme role for omitted paint values. Explicit
widget values still win, including false italic and Monochrome rendering.

The public configuration is documented in [Shared UI defaults](../../../theme.md).
The earlier physical-device captures describe the earlier source snapshot; they
are not relabeled as evidence for this follow-up. No protected spec or Dune files
are changed, and no source commit or push is included.

## Risks

- Numeric and semantic enum values must not accidentally become concrete at
  construction time. An explicit value equal to the baseline remains explicit.
- Native semantic colors cannot be replaced with fixed RGB constants without
  losing platform appearance and accessibility adaptation.

## Questions

No open questions. The user selected Theme inheritance on September 15, 2026:
all themeable shared defaults belong to Theme, and widget optional parameters
must not supply concrete defaults. Retain explicit overrides and native platform
appearance/accessibility behavior. No Dune or protected spec changes are needed.
