# Patch Size Frame Budget Research

## Problem

The framework caps wire frames at 16 MiB, but that safety limit does not say
how much patch work Flutter can decode, apply, build, and rasterize within a
60 Hz frame budget. There is no measured threshold connecting an OCaml patch's
encoded byte size and operation count to physical-device Flutter frame timing.

Patch bytes alone are not a sufficient workload definition: a large string
update, a batch of property changes, and creation of many visible widgets can
have the same encoded size while producing different renderer work. The
measurement therefore needs a fixed patch shape and an explicit device and
build mode.

## Proposal

Add a focused integration benchmark fixture that sends real OCaml-generated
patches through the native FFI runtime into `BonsaiFlutterRoot` on a physical
iPhone in Flutter Profile mode.

Use a column of visible keyed `Text` nodes as the fixed workload. Start with a
small initial tree, then replace the text and child set with progressively
larger batches. For every accepted patch, collect its encoded `patchBytes`,
operation count, dirty-node count, decode time, NodeStore apply time, Flutter
build time, and raster time. Warm the app before sampling and repeat sizes near
the first 16 ms crossing.

Report the first observed size whose corresponding Flutter frame exceeds
16 ms, together with the largest tested size that stays at or below 16 ms.
Treat this as a device- and workload-specific empirical boundary, not a global
protocol constant.

## Decision

Use action-scoped Flutter timelines as the authoritative source for build and
raster durations. A delayed `FrameTiming` callback can otherwise observe a
newer `NodeStore` revision than the frame it describes and misattribute an
older timing to the newly accepted patch. Keep frame debug instrumentation as
the source for patch bytes, operation count, dirty-node count, decode time, and
store-apply time, then join those values with the matching action timeline in
the integration-test driver.

Record the measured physical-device result in
`benchmark/PATCH_SIZE_PROFILE.md`. For the selected visible keyed-text workload
on the tested iPhone 13, the first size that exceeded the 16 ms budget in every
ascending and descending boundary sample was 33,803 bytes, containing 406
operations and 372 dirty nodes.

## Alternatives considered

### Dart-only synthetic frames

Constructing frames directly in Dart would isolate renderer cost, but it would
not measure the requested OCaml-to-Flutter path, isolate transfer, or real frame
presentation.

### Flutter widget-test pump timing

Widget tests use a synthetic test binding and do not provide representative
physical-device Profile build and raster timings.

### Random mixed widget trees

A mixed workload might resemble an application, but a byte threshold from it
would be difficult to reproduce or interpret. A homogeneous visible-text
workload gives a controlled first data point.

## Acceptance criteria

- A physical-device Profile run applies frames generated by an OCaml
  integration entrypoint through the normal runtime bridge.
- Each sampled result correlates encoded patch bytes and operation count with
  Flutter build and raster durations.
- The sweep identifies adjacent tested sizes around the first frame exceeding
  16 ms, with repeated samples near the boundary.
- The result records the device, OS, Flutter version, build mode, patch shape,
  and threshold definition.

## Risks

- Thermal state, device activity, and shader or font warm-up add variance; use
  warm-up runs and report distributions rather than a single cold frame.
- A column containing too many visible children can overflow or exercise a
  layout pattern unlike production lists. This is intentional for the chosen
  worst-case visible-node workload and must be stated with the result.
- The benchmark determines correlation for one patch shape only. Other patch
  shapes require separate sweeps before choosing any production guardrail.

## Consequences

- The repository has a reproducible physical-device Profile benchmark that
  sends real OCaml incremental patches through the native runtime bridge.
- The benchmark driver rejects action windows without complete build and
  raster frames instead of silently reporting partial timing data.
- The measured onset region is 32–34 KiB for the visible-text workload, with
  33.8 KiB consistently over budget across both sweep directions.
- Decode and transactional store apply remain below one millisecond near the
  boundary; Flutter widget build dominates the missed budget.
- Applications can use the result to motivate patch splitting and
  virtualization, but cannot treat 33.8 KiB as a universal protocol limit.
- New representative workloads require their own fixtures and distributions
  before they can establish production performance guardrails.

## Questions

- None. The target physical iPhone is connected, and the workload and 16 ms
  threshold are explicitly scoped above.
