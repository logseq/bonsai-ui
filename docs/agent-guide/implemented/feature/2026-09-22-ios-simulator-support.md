# iOS Simulator support

## Problem

The framework's only iOS target is a physical arm64 device. That choice
forces every iOS iteration loop — UI behavior checks, generated-host
verification, Mail/Gallery acceptance — through a provisioned physical
iPhone, a development team and `devicectl` installation. Contributors
without a device, and automated environments that cannot attach one
(agent-driven verification, CI runners), cannot build or launch any iOS
surface at all: the Swift module refuses to typecheck for the simulator,
the OCaml cross toolchain produces only iPhoneOS objects, and the CLI has
no simulator toolchain, build or launch path. The SwiftUI layer is exactly
where fast visual iteration is needed most.

The agreed [SwiftUI-only architecture](../../proposed/architecture/2026-09-11-swiftui-only-apple-backend.md)
explicitly selected physical iOS and listed Simulator as unsupported, so
this is a new decision, not a gap in the existing implementation. The
open question is whether to add simulator support *alongside* physical
iOS — never as a replacement for its acceptance gates.

## Proposal

Add `arm64-apple-ios26.0-simulator` as a supported configuration of the
existing `ios` target, reusing the existing layered toolchain machinery
rather than creating a parallel build system:

- A second OCaml 5.1.1 cross toolchain targeting the iOS Simulator SDK,
  installed into a dedicated global opam switch
  `bonsai-swiftui-ios-simulator`, producing complete objects stamped
  `IOSSIMULATOR`/arm64/minimum 26.0. The simulator switch reuses the
  `ios` findlib toolchain name, so Dune context `default.ios` and
  `dune -x ios` remain unchanged; the active global switch — not the
  toolchain name — selects device versus simulator content. (Decision:
  dedicated switch reusing the `ios` toolchain name.)
- A simulator variant of the SDK packages generated by the same
  repository machinery (`tool/ios/regenerate_sdk_repository.sh` and the
  lock inputs under `vendor/opam-ios/`), keeping the immutable
  compiler/dependency closure and replaceable framework SDK split.
- CLI surface: `--simulator` on the existing `ios` target —
  `bonsai-swiftui build ios --simulator` and `bonsai-swiftui run ios
  --simulator` — rather than a distinct `ios-simulator` target name. The
  flag selects the simulator switch, the simulator sysroot and the
  `xcrun simctl` install/launch path; `--development-team` and signing
  flags are no-ops under it because simulator builds are unsigned.
  (Decision: flag on the existing target.)
- Xcode host staging that lets device and simulator complete objects
  coexist in one generated project, selected by Xcode's platform
  variables rather than separate projects.
- Swift contract change: remove the `#error` for
  `targetEnvironment(simulator)` in
  `swift/BonsaiSwiftUI/Sources/PlatformSupport.swift` while keeping the
  Catalyst and non-arm64 rejections.
- The platform floor stays iOS 26.0 arm64, identical to the device
  baseline — no relaxed minimum for wider simulator coverage.
  (Decision: keep parity with the physical baseline.)
- Acceptance includes a hosted runtime XCTest executed inside the
  simulator, analogous to Mail's iPhone XCTest; UI-level XCTest is in
  scope for this decision. (Decision: require a simulator XCTest.)
- Examples may produce simulator captures for `docs/screenshots/`;
  simulator-sourced evidence is labeled as such and never substitutes
  for physical captures where a rule requires them. (Decision: examples
  can emit simulator screenshots.)
- Physical iOS remains the authoritative acceptance target; the
  simulator verifies build, launch, XCTest and OCaml state changes but
  does not replace device gates for input/IME, gestures or performance.

## Decision

The `--simulator` flag path is implemented: the simulator toolchain lives
in the dedicated `bonsai-swiftui-ios-simulator` opam switch reusing the
`ios` findlib toolchain name, the SDK gains a `simulator_sdk_package`
universe built from the same pinned source, `build`/`run`/`doctor`
`ios --simulator` route through `Ios_simulator_platform` staging
(`SUPPORTED_PLATFORMS="iphoneos iphonesimulator"`, `ARCHS=arm64`
override, unsigned `.app`), and `run` drives `simctl` boot/install/launch.
The iOS 26.0 arm64 floor matches the device baseline.

Verified on this machine's `iPhone 17` (iOS 27.0) simulator, SDK
regenerated from the implementation commit: toolchain install + manifest
verification of `IOSSIMULATOR`/arm64/minos-26.0 objects; `build ios
--simulator --profile debug` produces an unsigned `.app` embedding a
real `IOSSIMULATOR` complete object for both Counter and Mail; `run ios
--simulator` boots, installs, launches and renders the real Counter UI;
hosted XCTest executes inside the simulator — Counter increments real
OCaml state (`Count: 0` → `1` → `2`), Mail `MailRuntimeTests` 2/2 and
`MailUITests` 2/2 pass (expansion, attachment detail, swipe-to-archive
removing a message); `xcodebuild -destination 'platform=iOS Simulator'`
builds unsigned; `tool/test_swift_platforms.py` accepts the simulator
target and still rejects Intel macOS and Catalyst; a labeled simulator
screenshot ships under `docs/screenshots/swiftui-counter/`. OCaml gates
(`dune build @all @runtest @fmt`, 52 tool tests) and
`spec-dev-tool check --all` pass; iPhoneOS code paths are unchanged.

Physical iPhone acceptance remains authoritative and was not re-run for
this feature; the simulator covers build, launch, XCTest and OCaml state
changes only.

## Alternatives considered

### macOS target only (status quo)

The macOS target already drives the full OCaml↔Swift path without any
device, and `make swift-test` plus the window tests give a fast local
loop. Rejected as a complete answer: it cannot exercise UIKit-only
surfaces (safe area, keyboard/IME, haptics, iOS navigation idioms,
UIKit adapter code) — precisely the layer where simulator iteration has
value.

### Link the iPhoneOS complete object into a simulator build

Reuse `ios/iphoneos/arm64` artifacts for a simulator destination. Not
viable: Mach-O `LC_BUILD_VERSION` stamps `IOS` versus `IOSSIMULATOR`,
the iPhoneOS objects carry `-miphoneos-version-min` against the device
sysroot, and the simulator linker rejects device platform objects. A
simulator sysrooted toolchain is unavoidable.

### Distinct `ios-simulator` CLI target

Expose `build ios-simulator` / `run ios-simulator` as a separate target
name. Not selected: the flag keeps one command surface and models
simulator as a destination variant of the same iOS product, while the
artifacts, switches and SDK packages underneath stay disjoint either
way.

### One iOS switch hosting both toolchains

Install `ios` and `iossimulator` findlib toolchains in the existing
`bonsai-swiftui-ios` switch rather than a second global switch. Not
selected: a dedicated `bonsai-swiftui-ios-simulator` switch reusing the
`ios` toolchain name preserves today's `Plan.iphoneos_switch` semantics
and keeps each platform's verify path independent, for the smallest
plan change.

### Upstream `conf-simulator-ios` conditional

Restore upstream `conf-ios.4`'s conditional recipe (marker package
`conf-simulator-ios` flips sysroot/target flags) instead of a
repo-owned sibling conf. Rejected for the fixed recipe: the repo
deliberately pins immutable conf metadata in
`vendor/opam-ios/sdk-packages`, and the upstream conditional makes one
package's output depend on another package's presence, which weakens
the fixed-identity guarantee. A separate pinned conf package keeps both
toolchains immutable.

## Acceptance criteria

- The simulator toolchain installs into `bonsai-swiftui-ios-simulator`
  and verifies `IOSSIMULATOR`/arm64/minimum-26.0 on built objects.
- `bonsai-swiftui build ios --simulator --profile debug` produces an
  unsigned `.app` linking a real simulator complete object.
- `bonsai-swiftui run ios --simulator` boots a `simctl` device, installs
  and launches the app; the Counter example's button changes real OCaml
  state, mirroring the physical-device CLI verification.
- A hosted XCTest suite executes inside the simulator and passes,
  giving UI-level coverage parity with Mail's physical-device XCTest.
- `xcodebuild -destination 'platform=iOS Simulator'` builds a generated
  host without signing.
- `tool/test_swift_platforms.py` accepts the simulator target and still
  rejects Intel macOS and Catalyst.
- An example produces a simulator screenshot under `docs/screenshots/`,
  labeled as simulator capture.
- All existing iPhoneOS gates (cross-compiler tests, SDK verification,
  device preflight and examples) keep passing unchanged.

## Consequences

- `toolchain install/verify/show/remove iossimulator` manages the
  simulator switch; `bonsai-swiftui-ios` is untouched.
- Lock files keep a single-line or multi-line `depends: [...]` block —
  `Application_lock.parse` now scans entries inside the block instead of
  requiring line-bounded form (fixes a pre-existing parser bug that
  silently dropped mail's dependencies).
- Generated hosts stage `SUPPORTED_PLATFORMS="iphoneos iphonesimulator"`
  and per-platform entitlements; existing generated trees need one
  `bonsai-swiftui build`/`xcodegen` regeneration to pick this up.
- `docs/screenshots/` accepts simulator captures when labeled as such in
  the manifest and README.
- The SDK lock now pins `simulator_sdk_package` + runtime package
  versions alongside the device ones; `regenerate_sdk_repository.sh`
  emits both universes.

## Risks

- Simulator is more permissive than device (process APIs and some
  sandboxed behaviors succeed), so green simulator runs can hide
  device-only failures; physical acceptance must stay authoritative in
  review and CI.
- A second sysroot/closure/SDK roughly doubles the iOS toolchain surface:
  additional lock inputs, recipe revisions, verify scripts and CI lanes
  to maintain.
- The simulator runtime requires a downloaded iOS platform
  (`xcodebuild -downloadPlatform iOS`), adding a machine-provisioning
  prerequisite device builds do not have.
- UIKit behavior still differs from hardware (touch precision, actual
  keyboard arbitration, performance); simulator evidence — including
  `docs/screenshots/` captures — must be labeled as such in acceptance
  docs.
- Upstream `opam-cross-ios` simulator support is thinly maintained; the
  repo may end up owning the simulator conf and recipe adjustments
  anyway, as it already does for `conf-ios.4`.
