# iOS Simulator support

## Problem

The framework's only iOS target is a physical arm64 device. That choice
forces every iOS iteration loop — UI behavior checks, generated-host
verification, Mail/Gallery acceptance — through a provisioned physical
iPhone, a development team and `devicectl` installation. Contributors
without a device, and automated environments that cannot attach one
(agent-driven verification, CI runners), cannot build or launch any iOS
surface at all: the Swift module refuses to typecheck for the simulator,
the OCaml cross toolchain produces only iPhoneOS objects, and the CLI has
no simulator toolchain, build or launch path. The SwiftUI layer is exactly
where fast visual iteration is needed most.

The agreed [SwiftUI-only architecture](../../proposed/architecture/2026-09-11-swiftui-only-apple-backend.md)
explicitly selected physical iOS and listed Simulator as unsupported, so
this is a new decision, not a gap in the existing implementation. The
open question is whether to add simulator support *alongside* physical
iOS — never as a replacement for its acceptance gates.

## Proposal

Add `arm64-apple-ios26.0-simulator` as a supported target next to
`iphoneos`, reusing the existing layered toolchain machinery rather than
creating a parallel build system:

- A second OCaml 5.1.1 cross toolchain targeting the iOS Simulator SDK,
  installed into a dedicated global opam switch, producing complete
  objects stamped `IOSSIMULATOR`/arm64/minimum 26.0.
- A simulator variant of the SDK packages generated by the same
  repository machinery (`tool/ios/regenerate_sdk_repository.sh` and the
  lock inputs under `vendor/opam-ios/`), keeping the immutable
  compiler/dependency closure and replaceable framework SDK split.
- CLI surface parity: `bonsai-swiftui toolchain install|verify|show|remove
  iossimulator`, `build ios-simulator`, and `run ios-simulator` launching
  through `xcrun simctl` instead of `xcrun devicectl`. Simulator builds
  are unsigned and need no provisioning profile or development team.
- Xcode host staging that lets device and simulator complete objects
  coexist in one generated project, selected by Xcode's platform
  variables rather than separate projects.
- Swift contract change: remove the `#error` for
  `targetEnvironment(simulator)` in
  `swift/BonsaiSwiftUI/Sources/PlatformSupport.swift` while keeping the
  Catalyst and non-arm64 rejections.
- Physical iOS remains the authoritative acceptance target; simulator
  verifies build, launch and OCaml state changes but does not replace
  device gates for input/IME, gestures, performance or screenshots.

## Alternatives considered

### macOS target only (status quo)

The macOS target already drives the full OCaml↔Swift path without any
device, and `make swift-test` plus the window tests give a fast local
loop. Rejected as a complete answer: it cannot exercise UIKit-only
surfaces (safe area, keyboard/IME, haptics, iOS navigation idioms,
UIKit adapter code) — precisely the layer where simulator iteration has
value.

### Link the iPhoneOS complete object into a simulator build

Reuse `ios/iphoneos/arm64` artifacts for a simulator destination. Not
viable: Mach-O `LC_BUILD_VERSION` stamps `IOS` versus `IOSSIMULATOR`,
the iPhoneOS objects carry `-miphoneos-version-min` against the device
sysroot, and the simulator linker rejects device platform objects. A
simulator sysrooted toolchain is unavoidable.

### One iOS switch hosting both toolchains

Install `ios` and `iossimulator` findlib toolchains in the existing
`bonsai-swiftui-ios` switch rather than a second global switch. Viable
but changes the switch's contents and verification contract; a dedicated
switch preserves today's `Plan.iphoneos_switch` semantics. Kept as a
question rather than decided here.

### Upstream `conf-simulator-ios` conditional

Restore upstream `conf-ios.4`'s conditional recipe (marker package
`conf-simulator-ios` flips sysroot/target flags) instead of a
repo-owned sibling conf. Rejected for the fixed recipe: the repo
deliberately pins immutable conf metadata in
`vendor/opam-ios/sdk-packages`, and the upstream conditional makes one
package's output depend on another package's presence, which weakens
the fixed-identity guarantee. A separate pinned conf package keeps both
toolchains immutable.

## Acceptance criteria

- `bonsai-swiftui toolchain install iossimulator` creates a verified
  OCaml 5.1.1 simulator toolchain; `toolchain verify iossimulator`
  checks `IOSSIMULATOR`/arm64/minimum-26.0 on built objects.
- `bonsai-swiftui build ios-simulator --profile debug` produces an
  unsigned `.app` linking a real simulator complete object.
- `bonsai-swiftui run ios-simulator` boots a `simctl` device, installs
  and launches the app; the Counter example's button changes real OCaml
  state, mirroring the physical-device CLI verification.
- `xcodebuild -destination 'platform=iOS Simulator'` builds a generated
  host without signing.
- `tool/test_swift_platforms.py` accepts the simulator target and still
  rejects Intel macOS and Catalyst.
- All existing iPhoneOS gates (cross-compiler tests, SDK verification,
  device preflight and examples) keep passing unchanged.

## Risks

- Simulator is more permissive than device (process APIs and some
  sandboxed behaviors succeed), so green simulator runs can hide
  device-only failures; physical acceptance must stay authoritative in
  review and CI.
- A second sysroot/closure/SDK roughly doubles the iOS toolchain surface:
  additional lock inputs, recipe revisions, verify scripts and CI lanes
  to maintain.
- The simulator runtime requires a downloaded iOS platform
  (`xcodebuild -downloadPlatform iOS`), adding a machine-provisioning
  prerequisite device builds do not have.
- UIKit behavior still differs from hardware (touch precision, actual
  keyboard arbitration, performance); simulator evidence must be
  labeled as such in acceptance docs.
- Upstream `opam-cross-ios` simulator support is thinly maintained; the
  repo may end up owning the simulator conf and recipe adjustments
  anyway, as it already does for `conf-ios.4`.

## Questions

- Should the CLI expose a distinct target (`build ios-simulator`, `run
  ios-simulator`) or a flag on the existing target (`build ios
  --simulator`)? A distinct target name keeps artifacts, switches and
  SDK packages cleanly disjoint.
- Toolchain topology: a dedicated global `bonsai-swiftui-ios-simulator`
  switch reusing the `ios` findlib toolchain name (smallest plan change)
  or one `bonsai-swiftui-ios` switch hosting both `ios` and
  `iossimulator` toolchains (shared host packages)?
- Keep the minimum at iOS 26.0 arm64 only, matching the device baseline,
  or relax to the older physical floor for wider simulator coverage?
- What does simulator acceptance require beyond build + launch + OCaml
  state change: a hosted runtime XCTest in the simulator (like Mail's
  iPhone one), or is UI-level XCTest out of scope for this decision?
- Who consumes the target: contributor iteration and CI only, or should
  examples also produce simulator screenshots/evidence in
  `docs/screenshots/` (whose current provenance rules assume committed
  source and, for iOS, physical capture)?
