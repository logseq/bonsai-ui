# Opam installation

## Consumer contract

An application depends on installed opam packages. It does not clone the
framework, point at another checkout's `_build`, or manually configure library
search paths.

| Package | Installed content |
| --- | --- |
| `bonsai_swiftui` | OCaml UI, Bonsai driver, protocol and native backend libraries |
| `bonsai_swiftui_tool` | `bonsai-swiftui` CLI and its Swift/C resources and build helpers |
| `bonsai_swiftui_ios_sdk` | Physical-iOS compiler/runtime closure and framework, in the dedicated iOS switch |
| `bonsai_swiftui_test` | Optional headless UI test support |

The tool resolves native resources under
`$(opam var share)/bonsai_swiftui_tool/framework`. Opam owns these files. The
application's Xcode project references that installed package; users do not
maintain a separate framework source tree. Opam may compile source packages
during installation, as it does for other OCaml libraries.

## Install a release

Prerequisites are macOS 26+ on Apple Silicon, Xcode, Python 3.9+, opam and an
OCaml 5.1.1 switch. Activate the intended switch with `eval "$(opam env)"`.
The framework packages have not yet been published to a public opam repository.
Obtain the repository location from the release publisher; do not assume the
packages are already in the default opam repository.

For a locally delivered release, add the `repository` directory generated by
the maintainer command below. Keep the corresponding archive available until
opam has downloaded it:

```sh
opam repository add bonsai-swiftui /absolute/path/to/release/repository --this-switch
opam install bonsai_swiftui bonsai_swiftui_tool
```

For a published repository, replace the local path with its URL. Install both
packages from the same release. Optional test support is installed with
`opam install bonsai_swiftui_test`.

Create an application in an empty directory:

```sh
mkdir journal
cd journal
bonsai-swiftui init --name journal --bundle-identifier org.example.journal
bonsai-swiftui build macos --profile debug
bonsai-swiftui run macos --profile debug
```

Check the application sources, its generated opam manifest and
`bonsai-swiftui.sexp` into the application repository. The CLI generates and
synchronizes the native Xcode host. No framework environment variables are
needed. Xcode, the OCaml compiler and the installed packages remain build
prerequisites; the resulting App embeds the application runtime.

## iOS

The application also needs a compatible iOS cross-compilation SDK. The CLI
installs its bundled SDK release into the global `bonsai-swiftui-ios` switch,
leaving the active host switch unchanged. Install once, then verify and build:

```sh
bonsai-swiftui toolchain install iphoneos
bonsai-swiftui toolchain verify iphoneos
bonsai-swiftui build ios --profile release --development-team "$APPLE_DEVELOPMENT_TEAM"
```

If the switch is already installed, start with `toolchain verify`. For an
unsigned build check, replace the development-team option with `--no-codesign`.
The CLI selects the iOS switch and builds the OCaml object automatically.

Local installation and independent App linking are verified. Public SDK
publication remains pending; the current local release uses a checksum-identified
archive outside the framework checkout. It is not available from the default
opam repository. See [the CLI guide](swiftui-cli.md) for signing and device launch.

## Maintainer release packaging

From the framework worktree:

```sh
python3 tool/package_opam_release.py _build/opam-release
```

The new output directory contains:

- `bonsai-swiftui-<version>.tar.gz`: sources required to build the three packages,
  including native resources and generated protocol/default values.
- `repository/`: opam metadata with the archive URL and SHA-256 checksum for
  each package.

The package manifests supply the version and must agree. The archive includes
current tracked and non-ignored untracked source files in package directories;
it excludes build output and Git metadata. It is deterministic for identical
sources and modes. Existing output directories are rejected to prevent
accidentally replacing an already distributed release.

For a hosted release, pass `--archive-url` with the final immutable download
URL, then upload the archive and publish the generated repository. This command
only creates local artifacts; it does not upload or publish anything. Local
repositories embed an absolute file URL; regenerate at the delivery location
or use a hosted archive URL when distributing to another machine.

### Matching local iOS SDK metadata

When the framework source has not been published as a Git commit, generate the
SDK repository from the exact release archive instead of changing a commit lock
to describe an uncommitted checkout:

```sh
sh tool/ios/regenerate_sdk_repository.sh \
  --source-archive /absolute/path/to/release/bonsai-swiftui-0.1.0~dev.tar.gz
sh tool/ios/regenerate_sdk_repository.sh --check \
  --source-archive /absolute/path/to/release/bonsai-swiftui-0.1.0~dev.tar.gz
```

`--output PATH` selects an alternate repository directory. The generator reads
package metadata from the archive, records an `archive-sha256-...` identity, and
uses its actual checksum in opam download metadata. It does not label the archive
as a published commit. Invalid archives are rejected before replacing output.
The default generation mode still uses the immutable commit in
`tool/ios/sdk_repository.lock`.

After generation, package and install the CLI again so its installed resources
contain the matching SDK repository. Keep the source archive at its immutable
local location. For distribution to other machines, a published commit/release
and matching remote SDK repository remain necessary.

Run acceptance before publication:

```sh
python3 tool/test_package_opam_release.py
python3 tool/test_swiftui_opam_install.py
```

The installation test clones the active dependency switch using macOS
copy-on-write, relocates the copied compiler/findlib paths for the test fixture,
installs the release with opam, and builds/runs an independent
App without framework source variables or OCAMLPATH. It leaves the original
switch unchanged. It reuses previously installed third-party dependencies and
therefore does not establish clean-machine dependency solving. The existing
prefix-layout test remains available as a faster installation-boundary check.

source coverage, deterministic archives, hosted download URLs, and preservation
of existing output. The real opam installation test passed in 200.170 seconds.
Opam compiled and installed all three packages from the release archive. The
independent App built in Debug, Profile and Release, passed signature validation,
and changed Count: 0 to Count: 1 through an actual OCaml event handler. Child
command argument and exit-status propagation also passed.

The local release archive is `_build/opam-release/bonsai-swiftui-0.1.0~dev.tar.gz`,

artifacts, not a public release. The acceptance run did not modify the original

## Framework development

Only framework contributors running an uninstalled CLI need this setup:

```sh
dune build @all @install
export BONSAI_SWIFTUI_SOURCE_ROOT="$PWD"
export BONSAI_SWIFTUI_CLI="$PWD/_build/default/bonsai_swiftui_tool/bin/main.exe"
export OCAMLPATH="$PWD/_build/install/default/lib${OCAMLPATH:+:$OCAMLPATH}"
```

These paths belong to framework development and are not application installation
instructions.
